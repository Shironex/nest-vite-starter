This is a current-state inventory of every domain under
`apps/web/src/features/`, generated by reading each component's `.hooks.ts`
file (the file that owns state, queries, and mutations per the
[feature folder convention](/frontend/feature-folder-architecture/)). Every tRPC
procedure referenced below was found via a repo-wide grep for `trpc.<router>.<procedure>`
across `apps/web/src`.

## auth

Purpose: sign in, sign up, verify email, and reset a forgotten password.
Route wiring: `src/routes/auth.tsx` (layout, redirects to `/dashboard` if
already authenticated) plus `src/routes/auth/{login,register,forgot-password,reset-password,verify-email}.tsx`.

Feature-root file: `src/features/auth/AuthForm.hooks.ts` exports
`useAuthForm<TFieldValues>()`, shared wiring every auth form builds on: a
zod-resolved `react-hook-form` instance, `serverError` state, and
`handleServerError`: an `AppErrorCode`-aware mutation `onError` handler that
maps a structured code to friendly copy (via `getAppErrorCode`,
`src/lib/trpc-errors.ts`) or falls back to the raw message.

| Component                   | Purpose                                                                                                                                                                      | Key hook                                                                         | tRPC procedures                                                     |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| `AuthLayout`                | Shared card/header chrome around every auth screen                                                                                                                           | `useAuthLayout` (derives whether a header renders)                               | none                                                                |
| `LoginForm`                 | Email/password sign-in with "remember me" and a redirect target from the URL                                                                                                 | `useLoginForm`                                                                   | `auth.login` (mutation), `user.me` (invalidated on success)         |
| `RegisterForm`              | Account creation; routes to `/auth/verify-email`, forwarding `emailSent: false` if the welcome mail could not be queued                                                      | `useRegisterForm`                                                                | `auth.register` (mutation)                                          |
| `ForgotPasswordForm`        | Requests a reset email; shows a focus-managed confirmation block on success                                                                                                  | `useForgotPasswordForm`                                                          | `auth.forgotPassword` (mutation)                                    |
| `ResetPasswordForm`         | Consumes the `?token=` search param (never a prop, `props-must-be-visual`) to set a new password; offers "request a new link" on an expired/invalid token                    | `useResetPasswordForm`                                                           | `auth.resetPassword` (mutation)                                     |
| `VerifyEmail`               | Two modes in one component: auto-verifies once when a `?token=` is present, or shows a "check your email" screen with a resend form                                          | `useVerifyWithToken`, `useCheckYourEmail`, `useVerifyEmail` (reads route search) | `auth.verifyEmail` (mutation), `auth.resendVerification` (mutation) |
| `TurnstileField`            | Cloudflare Turnstile CAPTCHA field; falls back to the public always-pass test site key with a loud console error if `VITE_TURNSTILE_SITE_KEY` is unset in a production build | `useTurnstileField`                                                              | none                                                                |
| `FormError` / `FormSuccess` | Presentational banners; the caller owns the message state                                                                                                                    | none (hooks file is an empty placeholder to satisfy the sibling set)             | none                                                                |

Notable behavior: `LoginForm` and `RegisterForm` both call `resetCsrfToken()`
on success (a fresh session needs a token tied to it), and both keep their
submit button disabled through `isPending || isSuccess` so the UI doesn't
re-enable while the post-success navigation is still in flight.

## help

Purpose: replayable per-screen guided tours, offered once automatically and
available forever after as in-app help.

The feature is deliberately lopsided. `driver.js` (MIT, zero runtime
dependencies, dynamically imported so it never touches the 225 kB first-paint
budget) buys the spotlight cutout, the popover placement and the keyboard
model. Everything that decides whether the ninth tour is cheap is ours:

| File                                | Owns                                                                                              |
| ----------------------------------- | ------------------------------------------------------------------------------------------------- |
| `Help.tours.ts`                     | The registry: which tour belongs to which route, and the derived copy keys                        |
| `tours/<screen>.tour.ts`            | One tour, as data: an id, a route, a version and a list of `data-tour` anchors                    |
| `Help.engine.ts`                    | Lazy load, `waitForAnchor`, the reduced-motion branch, outcome detection, focus restore           |
| `Help.queries.ts` / `.mutations.ts` | Read and write per-user progress through `help.progressGet` / `progressSave` / `progressResetAll` |

| Component          | Purpose                                                                                                      | Key hook              | tRPC procedures                             |
| ------------------ | ------------------------------------------------------------------------------------------------------------ | --------------------- | ------------------------------------------- |
| `TourLauncher`     | The topbar "Help" control, and the one place a tour is ever started (click, auto-start or a settings replay) | `useTourLauncher`     | `help.progressGet`, `help.progressSave`     |
| `HelpToursSection` | The "Help and tours" settings panel: every tour, its screen, its status, replay and reset-all                | `useHelpToursSection` | `help.progressGet`, `help.progressResetAll` |

### Adding a tour

Three edits, no engine change and no migration:

1. `src/features/help/tours/<screen>.tour.ts`, an `ITour` naming its route and
   its anchors.
2. One import and one entry in `TOURS` in `Help.tours.ts`.
3. A `tours.<id>` block in `locales/en.json`.

Then put `data-tour="<anchor>"` on the elements. Copy keys are DERIVED
(`tours.<id>.<anchor>.title` / `.body`), so nobody writes a key by hand, and
`Help.catalog.test.ts` fails if the catalog is missing one.

### Anchors are attributes, never classes

`data-tour` and nothing else. That is what lets a screen be restyled without
breaking the tour that points at it, and it is why the registry stores a bare
anchor NAME rather than a selector.

### Degradation

- **Reduced motion**: `prefersReducedMotion()` is read once, before any
  choreography, and the answer is `animate: false`. A shortened animation still
  moves the pixels.
- **Keyboard**: driver.js focuses the popover on every step and traps Tab
  between the popover and the highlighted element; the engine adds the
  accessible name its close control ships without, and restores focus to
  whatever started the tour.
- **A missing anchor**: `waitForAnchor` (a `MutationObserver`, not a poll)
  resolves a late mount as soon as it appears. On timeout the step is dropped
  and reported to Sentry with its tour id and anchor, and the tour carries on.
  If no anchor resolves at all, the tour does not start and the screen renders
  no help control.

### Where progress lives

`TourProgress` (one row per user, a Json map of `tourId -> { completedAt,
version, dismissed }`), a sibling of `NotificationPreference`. The server holds
no registry of tour ids, so a renamed or removed tour is ignored by the client
rather than 500ing the read, and the ninth tour needs no migration.

## notifications

Purpose: realtime, persisted notifications. Postgres is the source of truth
(via `trpc.notifications.list`); `src/hooks/use-socket.ts` merges live
`NOTIFICATION` socket events directly into that TanStack Query cache entry ,
there is no separate notifications store.

| Component          | Purpose                                                                                                                                                   | Key hook              | tRPC procedures                                                                 |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------- | ------------------------------------------------------------------------------- |
| `NotificationBell` | Header bell with unread badge (`9+` cap) and a "mark all as read" action; mounts unconditionally inside the authenticated layout so the query always runs | `useNotificationBell` | `notifications.list` (query), `notifications.markAllRead` (optimistic mutation) |
| `NotificationItem` | One row in the bell's dropdown; marks itself read on click                                                                                                | `useNotificationItem` | `notifications.markRead` (optimistic mutation)                                  |

Both mutations follow the same optimistic pattern: `onMutate` cancels
in-flight `notifications.list` queries, snapshots the previous cache value,
writes the optimistic (all-read / one-read) version, and `onError` restores
the snapshot; `onSettled` always invalidates to reconcile with the server.

## shared

Purpose: components consumed by more than one domain.

| Component          | Purpose                                                                                                                                                             | Key hook                        | tRPC procedures                                                          |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------- | ------------------------------------------------------------------------ |
| `FileUploadZone`   | Drag-and-drop / click-to-browse image upload with per-file progress, client-side type/size validation, and duplicate-in-flight-name dedupe                          | `useFileUploadZone`             | `storage.requestUpload` (mutation, requests an S3 presigned POST policy) |
| `PasswordStrength` | Live checklist of password requirements, mirrored 1:1 from `PASSWORD_REQUIREMENTS` in `@repo/shared/schemas` (the same list the zod `passwordSchema` is built from) | `usePasswordStrength(password)` | none                                                                     |

`FileUploadZone`'s upload flow is a two-step presigned-POST: the hook calls
`storage.requestUpload` to get `{ url, fields, key, downloadUrl }`, then builds
a `FormData` via the exported `buildPresignedPostFormData(file, fields)`
helper (policy fields first, `file` last, S3 ignores anything appended after
the file field) and `POST`s it directly to storage over a raw `XMLHttpRequest`
(needed for upload progress events, which `fetch` cannot report).

## Cross-cutting hooks (`src/hooks/`)

Not feature-folder components (routes/hooks/stores are exempt from the
structural rules), but used by almost every feature above:

- **`use-auth.ts`**: `useAuth()`: wraps `trpc.user.me.queryOptions()` with
  `retry: false` and a shared `USER_ME_STALE_TIME` (5 minutes) that both route
  guards and this hook use, so they hit the same cache entry instead of
  triggering duplicate fetches.
- **`use-socket.ts`**: `useSocket(isAuthenticated)`: owns the Socket.io
  client lifecycle (connect on auth, disconnect on logout), toast-on-type for
  `NOTIFICATION` events, cache-merging for the same, `ACTIVITY` events into
  `useSocketStore`, and a "Connection lost" toast with a manual reconnect
  action after three consecutive failed connection attempts.
