# Decision record: how money is represented

**Date:** 2026-09-22
**Status:** deliberately undecided until billing lands
**Touches:** `packages/shared/src/money`, `packages/eslint-config/nestjs.js`
(`money-must-be-decimal`, dormant), the first billing module
**Reopens when:** the first code that stores, charges or displays a price is written. Whoever
writes it makes this decision first, using the analysis below, and records it here.

## Decision

Not chosen, on purpose. There is no money column and no billing code in the starter today, so a choice now would be made without a single call site to test it against. What is
recorded is the choice itself, so that it is made deliberately instead of by whichever line of
code happens to be written first.

## The state

- `packages/shared/src/money` is a decimal-string `Money` (`{ amount: string, currency }`) and
  recommends `Decimal @db.Decimal(p, s)` for columns. Its docblock notes that per-unit prices
  often need 4 fractional digits while totals need 2.
- `money-must-be-decimal` (`@noctcore/eslint-plugin-contracts`) is **dormant**: it is not
  enabled in `packages/eslint-config/nestjs.js`, because its name patterns (`total`, `sum`,
  `balance`, ...) would flag existing non-money numbers such as a pagination `total`. The
  comment above where it would be wired says it activates with the first money field.
- Stripe's API takes and returns **integer minor units** (`amount: 1999` for 19.99 USD). An
  allowance option for minor-unit fields in `money-must-be-decimal` is being built separately,
  so either option below can be enforced once chosen.

## The two options

### A. Minor units at the Stripe boundary, Decimal inside

Everything the product stores and computes is `Decimal` / decimal-string `Money`. Conversion to
integer minor units happens in exactly one place: the Stripe adapter, on the way out and on the
way in.

- **Costs:** a conversion module with its own tests (currency exponent table, rounding rule,
  refusal of sub-minor-unit amounts), and an allowance in `money-must-be-decimal` scoped to that
  one adapter directory.
- **Buys:** a tax rate applied to a 4-decimal unit price, proportional credits and currency
  conversion all happen in exact decimal arithmetic. It matches what `packages/shared/src/money`
  already says and what invoice or accounting output needs.
- **Risk:** the boundary is a single point that must round correctly. A bug there is a
  one-cent discrepancy per invoice, which an accountant will find.

### B. Minor units everywhere

Every amount is an integer count of the currency's minor unit, in the database, in the API and
in the UI, matching Stripe.

- **Costs:** `packages/shared/src/money` changes shape (or a second primitive appears beside
  it), `money-must-be-decimal` is configured to accept integer minor-unit fields everywhere, and
  any 4-decimal unit price cannot be stored at all without a second representation.
- **Buys:** no conversion at the Stripe boundary, integer arithmetic that cannot drift, and a
  data model that reads the same as Stripe's dashboard and webhooks.
- **Risk:** the first per-unit price below one cent, or the first percentage applied to an
  integer amount, forces a rounding decision at every call site instead of in one place.

## Guidance for whoever reopens it

For a SaaS subscription with whole-unit prices, B is simpler. For anything that prices per unit,
applies tax line by line, or produces accounting documents, A is the only one that stays exact.
A product that issues invoices leans A; a product that only ever charges a flat monthly fee leans
B. Decide per product, record it here, and enable
`money-must-be-decimal` in the same change with the matching allowance.
