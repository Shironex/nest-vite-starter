# Recipe: file uploads with S3

**When you need it:** users upload files (avatars, attachments, imports) and the api should not
carry the bytes. The starter has no storage code and its CSP allows no third-party upload target.

## Shape of the change

- **Storage.** An S3-compatible bucket (S3, R2, MinIO for development). Add a minimal client behind
  a small `StorageService` in `apps/api/src/common/storage/`, configured from new keys in
  `apps/api/src/config/env.ts` (endpoint, region, bucket, credentials) and `.env.example`. Refuse
  empty credentials in production, like the other secrets.
- **Presigned upload.** Two procedures on a new module, both behind `AuthMiddleware`:
  `files.createUpload` validates the declared type and size against an allowlist, creates a `File`
  row owned by `ctx.user.id` in a `PENDING` state, and returns a presigned `PUT` URL for a key the
  server chose (`<userId>/<fileId>`, never a client-supplied path). The browser uploads directly,
  then calls `files.completeUpload`, which checks the object exists with the expected size and flips
  the row to `READY`.
- **Download.** A procedure that returns a short-lived presigned `GET` URL after checking ownership.
  Keep the bucket private.
- **Web.** A feature with an upload hook that calls `createUpload`, `PUT`s the file, then calls
  `completeUpload`. Add the bucket origin to `connect-src` in
  `apps/web/docker/snippets/security-headers.conf` and to the api's helmet CSP if the api serves
  pages.

## The cross-user delete guard

Deletion is the procedure people get wrong. A `files.delete` that takes only a file id lets any user
delete any file by guessing ids. Always scope the lookup by the caller:

- Find the row with `where: { id, userId: ctx.user.id }` (and `deletedAt: null`). Not found and not
  yours must look identical to the client.
- Derive the object key from the row, never from input.
- Delete the row and the object together: row first (so a failure leaves an orphan object, which a
  sweep can reap, rather than a row pointing at nothing), written to the audit log outside any
  transaction.
- Cover it with a spec that signs in as user A, then calls delete on user B's file and expects a
  not-found answer and an untouched object. That spec is the guard.

## Pitfalls

- Declared size and type are only hints: enforce limits in the presigned policy (content length
  range) and re-check the object on completion. Sniff the type of anything you render back.
- Include the files in the account purge (`modules/user/user-purge.service.ts`) and in the data
  export, or deleting an account leaves its files behind.
- A `PENDING` row that never completes needs a `@Cron` sweep that deletes the row and any object.
- Set CORS on the bucket for the web origin only, and never return the storage credentials or a
  permanent public URL for private files.
